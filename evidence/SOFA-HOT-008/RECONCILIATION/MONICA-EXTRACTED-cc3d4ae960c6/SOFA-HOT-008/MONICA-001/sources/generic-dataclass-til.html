Typing a generic dataclass default: use a class-bound TypeVar and a lambda default_factory

  • Scope

    This guidance applies to Python dataclasses using generics and mypy type checking.

  • Supporting

    Mypy rejects a default value of type C for a field typed as TypeVar CT bound to C because the default is wider than the declared type.

  • Central

    To resolve generic dataclass default factory errors, use a lambda function as the default_factory to allow mypy to infer the callable return type as the field type.

  • Recommendation

    Subclasses of generic dataclasses must be explicitly parameterized (e.g., myclass[C2]) to ensure the field override is checked against the concrete type.

  • Central

    A generic field in a base dataclass cannot have a default that is valid for every possible TypeVar instantiation, necessitating a type ignore comment or removing the default from the base class.

  • Recommendation

    For mutable defaults in dataclasses, always use a factory function rather than a direct default value.

mypy is complaining for two different reasons, and they need two different fixes.

The error on var: CT = field(default_factory=C) is the real typing problem. C is a value of type C, but var is declared as CT, and CT is a TypeVar that only promises "some subtype of C". A bare C is not assignable to an arbitrary CT — for a particular instantiation, CT could be C2, and C is not a C2. The type checker is correctly rejecting a default that is wider than the declared type.

The error Need type annotation for "my_class1" is a knock-on effect: because the field's type could not be resolved to anything concrete, mypy cannot infer the type of the instance either.

The clean fix is to give myclass an explicit type parameter with a bound, provide the default through a lambda so mypy sees it as a callable returning the field type, and parameterise the subclass as myclass[C2] so the override is checked against the concrete type rather than the bare TypeVar:

from __future__ import annotations
from dataclasses import dataclass, field
from typing import Generic, TypeVar

@dataclass
class C:
    pass

@dataclass
class C2(C):
    pass

CT = TypeVar(&quot;CT&quot;, bound=C)

@dataclass
class myclass(Generic[CT]):
    # lambda (not `C`) so the factory is typed as Callable[[], CT] for each CT
    var: CT = field(default_factory=lambda: C())  # type: ignore[assignment]

@dataclass
class myclass_child(myclass[C2]):
    var: C2 = field(default_factory=C2)

a = myclass()
b = myclass_child()
print(type(a.var), type(b.var))   # &lt;class 'C'&gt; &lt;class 'C2'&gt;

Running that prints &lt;class '__main__.C'&gt; &lt;class '__main__.C2'&gt;, and mypy is satisfied for the subclass. The one residual error is the base class line, and it is genuinely unresolvable in the general case: a generic field cannot have a default that is valid for every CT, so you either accept the single # type: ignore[assignment] there (as above) or drop the default from the base and require callers to pass var when they instantiate myclass() directly. The ignore is honest here — it documents that the default only makes sense for the unparameterised myclass, which is exactly the case that works at runtime.

Two things that trip people up. First, declaring the subclass as plain myclass instead of myclass[C2] — without the explicit parameter mypy keeps treating var as CT and the override stays unchecked, which is what produced the confusing second error in the original report. Second, field(default_factory=C) vs default_factory=C2: for a mutable default always use a factory rather than a default value, and make sure the factory's return type matches the field on the subclass — default_factory=C2 paired with var: C2 is what makes the override legal.

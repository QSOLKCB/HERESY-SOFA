# HERESY-008 — The Git Identity Crisis

- **Hypothesis:** `GIT_DIR` overrides repository discovery even when `git -C` selects a different working directory. If the override refers to a valid other repository, `git add` can return zero while updating the wrong index.
- **Environment:** Python 3 standard library + Git CLI, with two disposable repositories containing spaces in their paths. Windows `cmd.exe` and network operations are not required or tested.
- **Expected (operator assumption):** `-C` picks the intended checkout's metadata, regardless of `GIT_DIR`.
- **Actual (executed Linux test):** `rev-parse` identifies the second repository; `status` observes a changed file; `add` stages the target's contents in the second repository; the intended repository's index stays unchanged. Clearing the override selects the intended metadata.
- **Mitigation:** Use `GIT_INSTALL_DIR` or `GIT_EXE` for executable paths, leave reserved Git variables unset unless intentionally needed, and inspect `rev-parse --absolute-git-dir` before sensitive mutations.
- **Fail-closed evidence:** The runner verifies seven observations, returning nonzero if any fail. Missing or stubbed Git cannot certify success. Machine-readable receipts are generated by the standard harness and should not be committed.
- **Limitations:** The original Windows batch script was not executed; no `git pull`, network I/O, real repositories, or original reporter behaviour is claimed.
